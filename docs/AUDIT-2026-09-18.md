# Kubi — Senior Engineering Audit

**Date:** 2026-09-18 · **Commit:** 5071ece · **Scope:** `firmware/`, `dashboard/`, `firmware/sim/`
**Audience:** planning agent. Findings are anchored to `file:line` and ordered by impact on the delivered gift.

---

## 0. Context that should shape prioritisation

This is a physical gift with a fixed recipient. That changes the calculus versus a normal product:

- Bugs that are **silent in the simulator but visible on the cube** are the most dangerous class here, because the simulator is the primary development surface. Two of the P0s below are exactly this.
- Bugs that are **intermittent** (the `String` race, P1-1) are near-impossible to debug once the cube is on someone else's desk.
- Features that are **wired but non-functional** (calendar sync, battery gauge) are worse than absent features — they advertise capability and then fail.

**What is genuinely strong** and should not be disturbed by refactors:

- The SITL digital twin is a real engineering achievement and rare at this scale. The managers really do compile unmodified for both targets.
- `ScheduleManager::getDaysFromCivil()` is Howard Hinnant's `days_from_civil` — correct calendrical arithmetic, not naive day counting.
- RFC 5545 line unfolding is actually implemented (`ScheduleManager.cpp:243-260`); most hobby ICS parsers skip it and break on long `SUMMARY` fields.
- NVS persistence is consistent and thorough across Pomodoro durations, colours, clock view, and iCal URL.
- Manager separation is clean, headers are narrow, and `AGENTS.md` captures real hard-won debugging (the trailing-backslash comment trap, orientation-transient tap suppression).

## P0 — Will be noticed by the recipient

### P0-1. The speaker is silent. Every chime is a no-op.

`AudioManager::init()` (`firmware/src/AudioManager.cpp:59-67`) configures pinout, rate, bit depth, channels and gain — but never calls `_i2sOut->begin()`.

In ESP8266Audio, `AudioOutputI2S::ConsumeSample()` opens with:

```cpp
//return if we haven't called ::begin yet
if (!i2sOn)
  return false;
```

`i2sOn` is set to `true` only inside `begin()`. Every sample written by `updateSynthesizer()` (`AudioManager.cpp:143-152`) is therefore discarded. All five chimes — Pomodoro completion, the 7-note long-break fanfare, tap feedback, wake ping, slam "ouch" — produce nothing on hardware.

**Why the simulator never caught it:** the desktop mock (`firmware/sim/include/AudioOutputI2S.h`) returns `true` unconditionally from every method including `ConsumeSample`, and the workbench plays its Web Audio chimes off the `lastChime` *telemetry string* (`sim_main.cpp:93-105`), not off the synthesised signal. The sim is structurally incapable of detecting this bug class.

**Fix:** call `_i2sOut->begin()` after `SetGain()` and check the return value. Treat the mock returning `true` as a bug in the mock.

### P0-2. Even once `begin()` is called, the synthesiser is throughput-starved.

`updateSynthesizer()` pushes a fixed **64 samples** per call. It is driven from `core1HardwareTask`, which ends in `vTaskDelay(10 / portTICK_PERIOD_MS)` (`main.cpp:349`) → ~100 Hz → **~6,400 samples/sec against a 22,050 Hz sample rate**, i.e. 29% of what the DMA consumes.

Compounding it: `ConsumeSample` calls `i2s_write(..., timeout = 0)` and `AudioManager` ignores the return value, so buffer-full conditions silently drop samples on top of the underrun.

**Fix:** drive audio from a dedicated small FreeRTOS task that blocks on `i2s_write` with a real timeout, or size each push to the elapsed wall-clock time rather than a fixed 64.

**Sequencing note:** P0-1 and P0-2 must land together. Fixing P0-1 alone turns silence into stutter, which is arguably a worse first impression.

### P0-3. Face 4 never fetches the calendar. There is no HTTP client in the firmware.

Verified: no `HTTPClient`, `WiFiClient`, or `WiFiClientSecure` usage anywhere in `firmware/src/`.

The data path is a dead end:

1. `POST /api/settings {icalUrl}` stores the URL in NVS (`API.cpp:83-90`).
2. `ScheduleManager::setIcsUrl()` (`ScheduleManager.cpp:124-136`) saves it and sets `_hasIcs = true`.
3. The "hourly sync worker" in `core0NetworkTask` (`main.cpp:242-246`) does nothing but `Serial.println("[CALENDAR] Hourly sync triggered")`.

**Consequence:** entering a Google Calendar URL flips the face out of its "No calendar connected, that's sad" state into a permanent "Nothing happening, I guess". The feature actively lies about its state. The only working path is manually uploading an `.ics` through the dashboard, which never refreshes afterwards.

This is the single largest functional gap in the project.

**Implementation note for planning:** a month of Google Calendar ICS is routinely 100–300 KB. The current load path (`ScheduleManager.cpp:198`, `icsContent = f.readString()`) pulls the entire file into a heap `String`, then `parseIcs` builds a second `std::string unfolded` copy of the same size. Two full copies of a 300 KB payload on a device with ~180 KB free heap will fail. **Stream-parse line by line** rather than bolting an `HTTPClient` onto the existing whole-file API.

### P0-4. Event times are displayed in UTC.

`parseIcs()` (`ScheduleManager.cpp:297-302`) extracts hours and minutes from the characters after `T` verbatim:

```cpp
timeStr = val.substr(tPos + 1, 2) + ":" + val.substr(tPos + 3, 2);
```

Google emits `DTSTART:20260918T140000Z` for timed events. Nothing strips or converts the trailing `Z`, and `TZID=` parameters are ignored entirely. At UTC+2 **every meeting displays two hours early**, and events after 22:00 local are bucketed onto the wrong day by the `diffDays` calculation.

Secondary: the sort comparator (`ScheduleManager.cpp:330-333`) uses `strcmp` on the time string, so `"All day"` sorts *after* every timed event because `'A'` (65) > `'0'` (48).

### P0-5. The screen never sleeps, and tap-to-wake is unreachable.

The sleep logic is circular and can never be entered:

- `_sleeping` is initialised `false` (`DisplayManager.cpp:15`) and `_wakeExpiryTime` `0`.
- `setSleep(true)` is reachable only from `DisplayManager::loop()`, guarded by `if (_wakeExpiryTime > 0 && ...)` (`DisplayManager.cpp:54-58`).
- `_wakeExpiryTime` is assigned only in `wakeScreen()` (`DisplayManager.cpp:50`).
- `wakeScreen()` is called only from `main.cpp:302`, inside `if (display.isSleeping())`.

Nothing can enter sleep, so nothing can ever wake. The backlight sits at 255 permanently. `MODE_NIGHT_SLEEP` is declared (`API.h:10`) and never entered. The vendored `Dusk2Dawn` sunrise/sunset library (`firmware/lib/Dusk2Dawn/`, 299 lines) is referenced nowhere — it is dead weight that was presumably intended for exactly this.

A full-brightness screen running 24/7 on a desk (possibly a bedroom desk) is the kind of thing that gets a gift quietly unplugged.

## P1 — Stability and correctness

### P1-1. Cross-core `String` races → intermittent reboots.

`screenOverrideText` and `secretIcalUrl` are plain Arduino `String` globals, **written from the AsyncTCP handler task** (`API.cpp:84`, `API.cpp:175`) and **read concurrently from `core1HardwareTask`** (`main.cpp:277`, `display.drawOverrideAlert(screenOverrideText)`).

A `String` assignment frees the old heap buffer and allocates a new one. A reader preempted mid-`drawString` dereferences freed memory. The `volatile` qualifiers on the neighbouring scalars (`main.cpp:25-31`) do nothing for this — `volatile` is not a synchronisation primitive, and it cannot make a two-word pointer+length update atomic.

This is the canonical random-reboot bug on dual-core ESP32, and it is intermittent enough to be miserable to diagnose remotely.

**Fix:** guard both with a `portMUX_TYPE` critical section around a copy into a local `String`, or double-buffer with an atomic index. Cheap either way.

### P1-2. Full-screen repaint at 20 Hz.

Every draw path opens with `_tft.fillScreen(TFT_BLACK)` and redraws everything, every 50 ms (`main.cpp:272`).

240 × 320 × 16 bit = 1.23 Mbit. At the configured `SPI_FREQUENCY=40000000`, that is **~31 ms just to clear the screen — 61% of the 50 ms frame budget** before a single glyph is drawn. On real hardware this reads as visible flicker and tearing, and it monopolises the SPI bus.

The code does not even need it: `setTextColor(fg, bg)` already paints its own background.

**Fix options, in order of effort:**

1. Drop `fillScreen` from the steady-state paths; clear only changed regions. Nearly free.
2. Repaint the clock face only on minute change. The schedule ticker genuinely needs the high tick rate; the clock does not.
3. `TFT_eSprite` per region (clock digits, timer, each schedule card). A full-screen 16-bit sprite is ~150 KB and will not fit alongside everything else — do **not** plan for one.

### P1-3. Unauthenticated API, and the calendar is served to the whole LAN.

`server.serveStatic("/", LittleFS, "/")` (`API.cpp:232`) serves the filesystem **root**, which contains `/calendar.ics` written by `setIcsContent()` (`ScheduleManager.cpp:170`). The recipient's full calendar is readable by anyone on the network at `http://kubi.local/calendar.ics`.

Separately, every endpoint is unauthenticated: anyone on the LAN can push arbitrary text to the screen (`POST /api/override`), wipe the calendar (`DELETE /api/calendar`), or change settings.

The open API on a home LAN is a defensible judgment call. **The calendar exposure is not** — it is a genuine privacy leak and a one-line fix: serve static content from a `/www` subdirectory and keep `calendar.ics` outside it.

### P1-4. OTA cannot work with the current partition table.

`platformio.ini:10` sets `upload_protocol = espota` and `main.cpp:206-228` runs `ArduinoOTA`, but `partitions.csv` defines a **single** app partition:

```
app0,     app,  ota_0,   0x10000, 0x200000,
spiffs,   data, spiffs,  0x210000,0x1E0000,
```

`esp_ota_begin()` refuses to write to the currently-running partition, so an OTA push should fail at `Update.begin()`. Two app slots are required.

The budget works: `firmware.bin` is 1.32 MB and `firmware/data/` is 556 KB, so `ota_0` and `ota_1` at 0x180000 (1.5 MB) each plus ~0x100000 (1 MB) for LittleFS fits inside 4 MB flash.

**Verify before planning around this** — confirm with an actual `pio run -t upload` over the network. If OTA has demonstrably worked, this analysis is wrong and it is worth understanding why.

### P1-5. Battery percentage is fabricated.

`batteryPercentage` is initialised to `100` (`main.cpp:27`) and is never written anywhere on the hardware path. The only writer in the codebase is the simulator's `/sim/inject` (`sim_main.cpp:533`). The dashboard gauge and `/api/diagnostics` report a constant 100%.

Either wire an ADC divider or remove the gauge. A permanently-full fake battery indicator on a gift is worse than no indicator.

### P1-6. Shake probably does not work on the two faces that advertise it.

`SensorManager::processMotion()` (`SensorManager.cpp:104-121`) detects shake purely from X-axis sign reversals across a ±3.0 m/s² deadzone:

```cpp
int currentSignX = (x > 3.0f) ? 1 : ((x < -3.0f) ? -1 : 0);
```

On Face 2 (Pomodoro) and Face 4 (Schedule), the cube rests X-dominant with |x| ≈ 9.8. `currentSignX` is pinned to ±1, and crossing to the opposite sign requires the shake to overcome gravity by ~12.8 m/s² (≈1.3 g). On Face 1 and Face 3 (where x ≈ 0) the same gesture crosses the threshold trivially.

The UI advertises shake precisely on Faces 2 and 4 (skip phase, jump to today). **Bench-test this on hardware.** The fix is to detect reversals on the *gravity-removed* component, or on whichever axis is currently non-dominant.

### P1-7. Motion deltas are computed over two sample periods, not one.

In `SensorManager::loop()` (`SensorManager.cpp:75-88`), `processMotion(x,y,z)` runs **before** the history shift:

```cpp
processMotion(x, y, z);     // reads _prevX
updateFace(x, y, z);
_prevX = _lastX;            // shift happens after
_lastX = x;
```

So `processMotion` for sample *n* compares against sample *n−2*, and `deltaMag` spans 40 ms rather than the intended 20 ms.

**Do not "fix" this blindly.** The `deltaMag > 7.0f` tap threshold and the `totalMag > 35.0f` slam threshold were clearly hand-tuned against the current (doubled) deltas. Correcting the ordering roughly halves `deltaMag` and will break tap detection. Treat it as a documented quirk, or re-tune both thresholds in the same change.

## P2 — Architecture

### P2-1. "Zero code duplication" is not true for the layer that matters most.

`AGENTS.md` §3 claims firmware sources are shared 1:1 with the simulator. The **managers** genuinely are. The **orchestration is copy-pasted**:

| Concern | Hardware | Simulator | Shared? |
|---|---|---|---|
| Main loop, gesture dispatch, face state machine, render switch | `main.cpp` `core1HardwareTask` (152 lines) | `sim_main.cpp` `hardwareSimulationThread` (189 lines) | No |
| REST API surface | `API.cpp` `setupAPIRoutes` (233 lines) | `sim_main.cpp` hand-rolled httplib routes (341 lines) | No |

`API.cpp` is not even in `build_sim.ps1`'s source list.

**Drift has already occurred:**

- `clockAnalogView` is `static` (file-local) in `sim_main.cpp:52`, but a shared non-static extern in `main.cpp:38` that `API.cpp:17` depends on.
- The simulator's `POST /api/settings {mode}` calls `display.setRotationForFace()` (`sim_main.cpp:361`); the hardware handler does not (`API.cpp:80-82`). **Changing face from the dashboard renders the face at the wrong screen rotation on the real cube, while looking perfect in the simulator.**
- Render tick is 40 ms in the sim (`sim_main.cpp:213`), 50 ms on hardware (`main.cpp:272`).

The entire value proposition of the digital twin is *"if it works in the sim it works on the cube."* Every divergence erodes that silently, and P0-1 is proof it already has.

**Highest-leverage refactor in the project:** extract the loop into a shared `KubiApp::tick()` and the API into transport-agnostic handlers (`handleState() -> String`, `handleSettings(const String&) -> String`). `main.cpp` and `sim_main.cpp` then become thin adapters of roughly 50 lines each: one binds to `AsyncWebServer`, the other to `httplib`.

Sequence this **before** the P0 fixes if further feature work is expected, and **after** them if the priority is shipping the cube. Doing the P0 fixes first means writing each one twice.

### P2-2. No tests, no CI.

Zero test files in the repository. No `.github/workflows` (the only workflow YAML is vendored inside `firmware/lib/WiFiManager/`).

The following are **pure logic that already compiles natively** under the existing clang toolchain, and are free to unit-test:

- `ScheduleManager::parseIcs` — unfolding, `DTSTART` variants, timezone handling, the 5-day ceiling, sort order. This is where P0-4 lives and where the P0-3 rewrite will introduce regressions.
- `PomodoroManager` phase machine — cycle counting, long-break transition at `_cycleTarget`, pause persistence.
- `hexToRGB565` / `rgb565ToHex` round-trip.
- `getCurrentPageItems` pagination arithmetic.

A `firmware/test/` directory plus a workflow running `pio run` + `npm run build` + the native tests would cover the regressions most likely to slip in. Self-hosted runners are already available, so CI here costs nothing but setup.

### P2-3. Dead code and stale artefacts.

- **`drawClockFace` ignores its `nextEvent` and `ticker` parameters entirely** (`DisplayManager.cpp:96-130`). Both `main.cpp:283` and `sim_main.cpp:232-233` pass hardcoded `"Design Review 14:00"` and `"^ AAPL +1.2% | BTC $92k"`. The fake data is inert, but the dead parameters invite someone to "fix" the wrong layer.
- **`KubiState` in `App.tsx:52-69`** declares `isNightMode`, `planetDawnH/M`, `planetDuskH/M`, `alarmHour/Minute`, `cfgSundownHour/Minute`. None exist in the firmware API; none are read by any component. They appear only in the interface and in `DEFAULT_STATE`.
- **The `/sim` workbench ships to the cube.** `Simulator.tsx` is lazy-loaded (`main.tsx:8`) but its chunk is built into `firmware/data/assets/` and flashed to LittleFS, where it can only ever try to reach `127.0.0.1:8080`. Wasted flash plus a broken route on the gift. Exclude it from the hardware build.
- **`dashboard/dist/`** is a stale April build; Vite now outputs to `firmware/data/` (`vite.config.ts` `outDir`). Gitignored, but confusing on disk.
- Unused overloads: `drawScheduleFace(const std::vector<String>&, int)` and two `drawClockFace` convenience overloads (`DisplayManager.h:23-29`).
- `clockShowDetails` / `clockDetailsTimeout` are maintained every frame (`main.cpp:36-38`, `265-268`) but never rendered.

### P2-4. Smaller items, for the record.

- **Lossy colour round-trip.** `hexToRGB565` → `rgb565ToHex` is not identity (888 → 565 → 888). The dashboard reads back a *different* hex than the user picked, so the colour swatch drifts on every reload. NVS already stores the original hex (`PomodoroManager.cpp:197-199`) — echo that instead of the round-tripped value in `/api/state`.
- **Dashboard masks disconnection.** `App.tsx:143-157` catches all fetch failures and returns `DEFAULT_STATE`. When the cube is offline the dashboard silently renders plausible fake data (100% battery, 22.0 °C, 25:00 timer) with no indication it is not connected. The `/sim` page handles this correctly with an `isConnected` flag — the main dashboard should too.
- **Function-`static` state inside a class method.** `SensorManager::updateFace` uses `static int candidateFace` / `static uint32_t faceCandidateStartTime` (`SensorManager.cpp:130-131`). Correct today because there is exactly one instance, but it is shared across all instances by definition — a landmine if a second `SensorManager` is ever constructed.
- `AudioManager` `new AudioOutputI2S()` is never deleted. Harmless for a singleton; noted for completeness.
- Simulator `/sim/frame` reads `sim_framebuffer` with no lock while the hardware thread writes it (`sim_main.cpp:500`). Torn frames only — cosmetic, sim-only, not worth fixing.

## Suggested sequencing

**Track A — make the gift work (before it ships):**

1. P0-1 + P0-2 together — audio `begin()` and the throughput fix. Verify on hardware, not in the sim.
2. P1-1 — mutex the shared `String`s. Small, and it prevents the worst class of post-delivery failure.
3. P0-5 — make sleep reachable; wire `Dusk2Dawn` or a simple hour window.
4. P1-3 — move static serving to `/www` so the calendar stops being LAN-readable.
5. P1-2 option 1 — drop `fillScreen` from steady-state paths.

**Track B — make Face 4 real:**

6. P0-4 — timezone handling in `parseIcs`, plus the `All day` sort fix. Cheap, and a prerequisite for 7 being useful.
7. P0-3 — streaming `HTTPClient` fetch with chunked parsing. The largest single piece of work in this list.

**Track C — before any further feature work:**

8. P2-1 — collapse the duplicated orchestration and API into shared code. Every item above otherwise has to be written twice.
9. P2-2 — native tests for `parseIcs` and the Pomodoro state machine, then CI.

**Verify on hardware before planning:** P1-4 (OTA/partitions) and P1-6 (shake on Faces 2/4). Both analyses come from source reading only and would change the plan if they do not reproduce.
